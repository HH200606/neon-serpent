## 1. 背景与问题定义

### 1.1 为什么还要做一个贪吃蛇

贪吃蛇是被实现得最多的游戏之一，这既是机会也是陷阱：**用户没有学习成本，但也没有期待**。真正决定它能不能被记住的，不是玩法创新，而是三件很容易被做砸的事：

1. **手感**：移动是否平滑、转向是否跟手、死亡是否有反馈；
2. **节奏**：难度是否在正确的时间点上升，让人「差一点就吃到」而不是「怎么突然这么快」；
3. **进入成本**：打开到能玩要几秒、手机上能不能玩、有没有广告和注册。

大多数玩具级复刻在这三点上都做了妥协——它们能跑，但不好玩。

### 1.2 问题陈述

> 想要在碎片时间玩一局的人，很难找到一个**打开即玩、手感扎实、手机上也能玩**的贪吃蛇；而能做到这些的实现，往往又绑定了引擎、素材包和构建流程。

拆成三个可验证的子问题：

| 编号 | 子问题 | 当前观察 |
| :--- | :--- | :--- |
| P1 | 移动按格跳，速度一快就像在瞬移 | 大量 Canvas 复刻用 `setInterval` / 直接按帧位移，没有插值 |
| P2 | 难度曲线靠「硬调」，玩家感受不到成长 | 只加快速度、不加机制，20 秒后就只剩焦虑 |
| P3 | 手机上不可玩或误触严重 | 只支持键盘；滑动与页面滚动打架 |

### 1.3 设计立场

这个产品的目标不是「做一个流行的游戏」，而是**用最小的技术面，把一件事做到可感知的好**。因此明确的取舍是：

- 不做玩法创新，把预算全部投在**手感、节奏、进入成本**上；
- 不使用任何图片与音频素材（版权干净、加载为零、可离线）；
- 保持零依赖、无构建，让「打开源码就能改」成为产品的一部分。

### 1.4 备选方案与取舍

| 方案 | 优点 | 缺点 | 结论 |
| :--- | :--- | :--- | :--- |
| 用 Phaser / Cocos 做 | 生态成熟、功能多 | 引入 200KB+ 引擎，失去「零依赖」这一差异点 | 否 |
| 用现成素材包（图 + 音） | 观感上限高 | 版权与加载成本，且与「代码即美术」的定位冲突 | 否 |
| 做玩法创新（多蛇、地形） | 有新鲜感 | 学习成本上升，违背「零学习成本」的前提 | V2 再评估 |
| **零素材 + 精修手感（本题）** | 加载极快、可离线、差异点清晰 | 美术上限受限于代码绘制 | **是** |

## 2. 目标与非目标

### 2.1 目标（按优先级）

| 编号 | 目标 | 衡量方式 |
| :--- | :--- | :--- |
| G1 | 打开即可玩，3 秒内进入第一局 | 从页面加载到 `playing` 的中位时间 ≤ 3s（含用户反应） |
| G2 | 手感成立：不跳格、转向跟手、死亡有反馈 | 移动插值覆盖率 100%；输入→转向的生效延迟 ≤ 1 帧 |
| G3 | 一局有「还想再来」的张力 | **再来一局率 ≥ 30%**；单局时长中位数 45–120s |
| G4 | 手机上真的能玩 | 375px 宽可完整游玩；误触率 ≤ 5% |

### 2.2 非目标（明确不做）

| 非目标 | 理由 |
| :--- | :--- |
| 账号体系 / 云端存档 | 单局 1–2 分钟的游戏，登录是纯粹的流失点 |
| 排行榜 / 多人对战 | 用户基数不足以让榜单有意义，且会把「自洽的难度」变成「被虐」 |
| 内购 / 广告 | 定位是开源作品集与公共小游戏 |
| 关卡编辑器 / 皮肤系统 | 会引入状态管理复杂度，收益与一期目标不符 |
| 玩法机制大改（如加入地形、传送门） | 违背「零学习成本」前提，V2 单独立项评估 |

## 3. 用户与场景

### 3.1 目标用户

| 画像 | 特征 | 关键需求 | 触发场景 |
| :--- | :--- | :--- | :--- |
| **A. 碎片时间玩家**（核心） | 通勤、排队、开会前 5 分钟 | 立刻能玩、一局能结束、不占流量 | 手机浏览器、社交链接 |
| **B. 复古/霓虹美学爱好者** | 喜欢 CRT、赛博朋克视觉 | 视觉调性统一、有质感 | 从设计社区/分享图进入 |
| **C. 前端同行** | 会顺手看源码 | 代码干净、有可读的实现取舍 | GitHub / 技术社区 |
| **D. 演示/整活用户** | 想录屏、想发朋友圈 | 有自动演示模式、画面好看 | `?demo=1` |

### 3.2 关键用户旅程（JTBD）

> 当我**手上有 2 分钟空档**时，我想**立刻玩一局有点挑战、输了还想再来一次的小游戏**，这样我**能把这段碎片时间填得舒服**。

必须避免的失败路径：

- 打开先黑屏/白屏等资源（→ 34KB 内联资源，无外部请求）；
- 第一次转向没反应或反向自杀（→ 同轴反向禁止 + 输入立即生效）；
- 手机上一划就整页滚动（→ `touch-action: none` + 滑动阈值）；
- 死了不知道为什么会死（→ 死亡粒子 + 屏幕抖动 + 结算面板）。

## 4. 成功指标

### 4.1 指标体系

| 层级 | 指标 | 定义 | 目标（假设） | 当前 |
| :--- | :--- | :--- | :--- | :--- |
| **北极星** | 再来一局率（RR） | 结算后 10 秒内再次开始 / 完成一局 | ≥ 30% | 未埋点 |
| 输入 | 开局率 | 进入 `playing` / 打开页面 | ≥ 65% | 未埋点 |
| 输入 | 单局时长中位数 | `playing`→结算 | 45–120s | 未埋点 |
| 输入 | 分数中位数 | 结算分数 | 100–250 | 未埋点 |
| 输入 | 连击达成率 | 达到过 ≥×3 的玩家占比 | ≥ 25% | 未埋点 |
| 输入 | 死亡归因分布 | 撞墙 / 自咬 | 撞墙 60–75% | 未埋点 |
| 输出 | 分享率 | 触发分享/复制链接 | ≥ 5% | 未实现 |
| 护栏 | 帧率 P95 | 中端机 | ≥ 58fps | 待测 |
| 护栏 | 首屏可交互 | 4G / 本地 | ≤ 600ms / ≤ 150ms | 待测 |
| 护栏 | 手机误触率 | 同局内无效滑动 | ≤ 5% | 未埋点 |

> ⚠️ **诚实说明**：一期上线时**没有任何埋点**，以上目标值是待验证假设。第 11 节给出最小事件集与口径。

### 4.2 指标设计原则

1. **不看 PV**，只看「再来一局率」与「单局时长」——它们直接对应「好不好玩」；
2. 分数中位数是**难度健康度**：过高说明太简单，过低说明挫败；
3. 护栏优先：帧率或误触一旦超标，先修体验再谈传播。

## 7. 游戏设计规格

### 7.1 核心循环

```
观察 → 决策转向 → 吃果实 → 分数/长度增长 → 速度上升 → 风险上升 → 死亡 → 结算 → 再来一局
```

单局目标 45–120 秒；一名普通玩家首局预期分数 60–150，熟练玩家 300+。

### 7.2 难度与张力来源

| 来源 | 机制 | 作用 |
| :--- | :--- | :--- |
| 速度 | 每果 ×0.978，76ms 封顶 | 前 20 秒温和，30 秒后紧张 |
| 连击 | 2.6s 窗口，×1–×5 | 制造「要不要冒险再吃一个」的决策 |
| 金果实 | 每 5 果、存在 9s、+30 | 高价值目标，诱发走位冒险 |
| 空间 | 24×24，身体持续变长 | 后期自咬风险指数上升 |

### 7.3 手感参数（真实值）

| 参数 | 值 | 说明 |
| :--- | :--- | :--- |
| 网格 | 24 × 24 | 单屏可完整容纳 |
| 初始步长 | 150 ms | 首局不至于手忙脚乱 |
| 步长下限 | 76 ms | 人手反应极限附近 |
| 加速系数 | 0.978 / 果实 | 约 20 个果实后接近上限 |
| 连击窗口 | 2600 ms | 约 17 步（150ms）内续上 |
| 倍率上限 | ×5 | 避免分数爆炸 |
| 金果实间隔 | 5 个普通果实 | 约每 8–12 秒一次 |
| 金果实寿命 | 9000 ms | 够绕 1.5 圈去拿 |
| 滑动阈值 | 24 px | 防误触 |
| 粒子上限 | 320 个 | 保帧率 |

### 7.4 死亡与反馈

- 死亡瞬间：粒子迸发（26 颗）、屏幕抖动（12px）、音效下滑；
- 结算面板：本局分数、最高分、「再来一局」按钮；
- 无「复活」设计——一局一命，保证风险真实。

## 9. 交互与状态

### 9.1 状态机

```
ready ─开始→ playing ─暂停→ paused ─继续→ playing
playing ─死亡→ dying ─0.6s→ over ─重开→ playing
playing ─切后台→ paused
```

### 9.2 边界场景

| 场景 | 期望行为 |
| :--- | :--- |
| 连续快速按两个方向 | 只接受第一个有效转向，第二个若反向则忽略 |
| 死亡瞬间点击重开 | 死亡动画结束前不可开始，避免误触 |
| 手机竖屏旋转为横屏 | 画布重排、不中断对局 |
| 长按滑动 | 只触发一次转向（不是连续转向） |
| 静音后刷新 | 仍为静音 |
| 打开即切后台 | 返回时处于暂停，不自动开始 |

## 12. 技术方案概要

| 层 | 实现 |
| :--- | :--- |
| 渲染 | Canvas 2D；`devicePixelRatio` 上限 2.5；`requestAnimationFrame` 单循环 |
| 逻辑 | 固定步长累加器（`acc >= stepTimer` 时推进一格），渲染按 `acc / stepTimer` 插值 |
| 输入 | `keydown`（方向/WASD/空格/M/R）+ Pointer 事件（滑动、D-pad） |
| 音频 | 懒加载 `AudioContext`，振荡器 + 指数包络 |
| 持久化 | `localStorage`（best / muted），异常捕获降级 |
| 结构 | `index.html`（80 行）+ `css/style.css`（323 行）+ `js/game.js`（769 行） |
| 发布 | GitHub Pages（main 分支根目录），无构建 |

**已知技术债**：`game.js` 为单文件 769 行、14 个小节；继续加功能前建议拆分为 `loop / state / render / audio / input` 五个模块，否则可维护性会先于功能触顶。

## 13. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
| :--- | :--- | :--- | :--- |
| 品类同质化，用户「玩过就不再打开」 | 高 | 高 | 靠手感与视觉差异，配合成绩卡分享；后续做每日挑战（固定种子）提供复访理由 |
| 难度曲线失衡（太易/太难） | 高 | 中 | 埋点看分数中位数与死亡归因，按数据调 150ms/0.978/2600ms 三个旋钮 |
| 手机误触（滑动与滚动冲突） | 中 | 中 | `touch-action: none` + 24px 阈值 + 屏幕方向键兜底 |
| 低端机掉帧 | 中 | 中 | 粒子上限 320、只在蛇头用 `shadowBlur`、DPR 上限 2.5；后续加自动降级 |
| 音频被浏览器拦截 | 低 | 中 | 首次手势后再创建 AudioContext；失败静默降级 |
| 单文件过肥难以维护 | 中 | 高 | 见技术债；V1 内完成模块拆分 |
| 被误认为「抄的某个复刻」 | 低 | 低 | 零素材、代码自绘，差异点可自证 |
